## ✅ 17.08.2026 — Критический фикс лаунчера + инкрементальные операции студии

### Задача

«Довести GreenBlox до идеала». Аудит показал: сборки чистые, движки синхронны,
БД и API живы, но были найдены 4 реальные проблемы — одна из них критическая.

### Критический баг: гость без аккаунта вообще не мог играть

1. **`POST /api/sessions`, `POST /api/sessions/sync` и `GET /api/sessions` требуют
   авторизацию** (401 без `x-gbtoken` — проверено по коду `sessions/route.ts`).
2. **`App.handlePlayGame` всегда ставил `multiplayer: true`** — даже для
   локальной сессии без `userId`/токена (пользователь не входил в аккаунт).
   Итог: неавторизованный игрок нажимал «Играть» → `createSession` → 401 →
   «Не удалось подключиться к мультиплееру» → игра не запускалась вовсе.
   Роблокс-клоны обязаны давать играть и без входа (гость = оффлайн-режим).

- [x] **`App.tsx`**: `handlePlayGame` включает `multiplayer` только когда
      `session?.userId` реально есть. Гость с local-only сессией запускает
      игру оффлайн: сольный забег без кода и sync-запросов (как Roblox guest).
      Авторизованный игрок по-прежнему хостит сессию с кодом.

### Студия: инкрементальные добавление/удаление (убраны лишние rebuildScene)

1. **Добавление сущности делало полный `rebuildScene()`** на каждую добавленную
   сущность. Ctrl+V кластера из 10 объектов = 10 полных пересозданий всего
   мира (O(N²) для мировой геометрии) — секундные фризы.
2. **`handleDeleteSelectedEntity` вызывал `renderer.rebuildScene()`** после
   удаления — это откатывало оптимизацию инкрементального удаления
   (`removeEntityMesh`), внедрённую ранее: Delete на большом мире снова фризил.
3. **Дублирующие `rebuildScene()`** в `handleAddCharacter` и `ensureRuntimePlayer`
   — полная пересборка мира ради одной/двух сущностей (сигнал `onEntityAdded`
   и так создавал меши).

- [x] **`page.tsx` — `addSub`**: теперь `renderer.createOrUpdateMesh(entity)` для
      конкретной добавленной сущности (сигнал приходит по одному на каждую,
      включая детей). Ctrl+V больше не пересобирает весь мир.
- [x] **`page.tsx` — `handleDeleteSelectedEntity`**: убран `rebuildScene()` —
      меши удалённых сущностей (и их детей) убирает `removeEntityMesh` из
      подписки `onEntityRemoved`.
- [x] **`page.tsx` — `handleAddCharacter`/`ensureRuntimePlayer`**: убраны лишние
      `renderer.rebuildScene()` — меши создаёт подписка. Рантайм-аватар попрежнему
      подменяет куб Player через `createOrUpdateMesh` при `setSimulationActive(true)`.

## ✅ 17.08.2026 — Большая оптимизация: студия и студийные карты перестали лагать (ноутбуки / Edge)

### Проблема

Пользователь: «студия лагает на ноутбуках или в Microsoft Edge, и карты, сделанные в
Studio, тоже очень лагают». Аудит студийного рендерера, физики, ECS и обоих игровых
движков выявил 6 независимых причин.

### Найдено при аудите

1. **Shadow map пересчитывалась на каждый кадр орбиты камеры.** В студии
   `shadowMap.autoUpdate` был включён — при каждом движении камеры three.js заново
   рендерил ВСЕ части мира из перспективы солнца. На студийных мирах с тысячами
   частей это половина стоимости каждого кадра (и лаг в Edge на слабых iGPU).
2. **Полный `rebuildScene()` при удалении ОДНОЙ части.** Обработчик
   `ecs.onEntityRemoved` пересоздавал ВСЕ меши мира — на большом проекте секундный
   фриз на каждый Delete.
3. **Grounded-проверка игрока перебирала ВСЕ сущности каждые 16 мс.** В
   `physicsWorld.updatePlayerController` стоял O(N) скан всего мира — на картах с
   тысячами частей это лишняя нагрузка в play-режиме.
4. **`getAllEntities()` аллоцировал новый массив на каждый вызов.** Рендерер и
   физика звали его десятки раз за кадр → GC-мусор.
5. **Merged-меш ВСЕГО мира лишал фрустум-куллинга.** Движок игры мёржил все
   статичные части в несколько гигантских мешей — GPU рисовал весь мир даже когда
   камера смотрит в одну сторону. Это был главный лаг студийных карт.
6. **Дорогие `backdrop-filter: blur(18px)` на панелях студии.** Blur на огромных
   панелях (шапка, правая панель, чипы) поверх WebGL — тяжёлая операция для
   слабых iGPU (Edge на ноутбуках), постоянная композиция каждый кадр.

### Что сделано

- [x] **Студийный рендерер**: `shadowMap.autoUpdate = false` + `markShadowDirty()`
      (тень перегенерируется только при реальном изменении геометрии/света/гизмо —
      не при вращении камеры).
- [x] **Студийный рендерер**: `removeEntityMesh(id)` — инкрементальное удаление
      меша сущности без пересоздания всех мешей мира (page.tsx вызывает его из
      `onEntityRemoved` вместо `rebuildScene()`).
- [x] **Студия**: `physicsWorld.updatePlayerController` использует кэш
      `staticColliders` для grounded-проверки вместо O(N) скана всех сущностей.
- [x] **ECS**: `getAllEntities()` возвращает закэшированный массив (обычный JS-массив,
      а не аллокацию на каждый вызов); инвалидация только при add/remove/update.
- [x] **Движок игры (ОБА)**: `flushStaticBatch()` переведён на **региональный
      бэтчинг** — части группируются по ячейкам ~80×80 юнитов (`BATCH_REGION`).
      Фрустум-куллинг three.js теперь отсекает невидимые области мира целиком,
      draw calls остаются низкими. Главный выигрыш для больших студийных карт.
- [x] **Студия (CSS + компоненты)**: убраны `backdrop-filter: blur(18/20px)` с
      панелей и чипов (заменены на плотную полупрозрачность `rgba(…, 0.94–0.96)`) —
      композиция стала дёшевой, вид сохранён.
- [x] Движок лаунчера и GreenBloxENGINE синхронизированы (региональный бэтчинг в ОБА).

## ✅ 16.08.2026 — Мультиплеер починен: StrictMode-гонка убивала сессии (выброс, статус «в сети», вход по коду)

### Проблема

Пользователь: «после последних фиксов мультиплеер перестал работать — при заходе

вход по коду не работает». Все три симптома — одна корневая причина.

Бэкенд мультиплеера (E2E) работал идеально: создание/join/sync — 200. Значит,
проблема клиентская. Виновник — **race-условие React StrictMode** в
`GameSession.tsx`:

- `main.tsx` оборачивает приложение в `<StrictMode>` → в dev каждый effect
  монтируется дважды: `mount → unmount → mount`.
- При первом mount мультиплеерный эффект запускает `boot()`
  (`createSession`/`joinSession`) — промис в полёте. Синхронный unmount ставит
  `cancelled = true`, но запрос ещё не вернулся.
- Второй mount запускает второй `boot()`. Оба запроса уходят на сервер.
- `socialStore.createSession` **идемпотентен** (reuse по `hostUserId + placeId`),
  `joinSession` просто повторно добавляет нас → оба mount'а получают **ОДНУ И ТУ

- Когда промис мёртвого первого mount резолвится, он видит `cancelled=true` и
  вызывает `leaveSession(session.id)` → **хост удаляет всю сессию, гость
  выбрасывается из состава** (E2E: олдовый leave → `GET ?code=…` = 404).
- Живой второй mount синкает мёртвую сессию → `syncFull` возвращает `[]` →
  срабатывает детект «🕒 Сессия закрыта — возврат в лаунчер» → игрок вылетает
  из плейса.
- У друзей при этом статус сбрасывается на `online` (в `leaveSession`), а
  сессия/бейдж «В игре» исчезает → «друг в сети, но не видно что играет».
- Join по коду: `GET ?code=` и `join` отдают 404, потому что сессии физически
  нет → «вход по коду не работает».

  - Все `leaveSession` (в `boot()` при `cancelled`, в cleanup) заменены на

## 15.08.2026 — Физика: персонаж застревал на платформе (ходил только после прыжка)

1. **Критический: движок пересоздавался при смене цвета аватара.**
   В `GameSession.tsx` конструктор `RobloxEngine` вызывался в `useEffect`,
   зависимостью которого был `colors`. Любое изменение облика в игровом меню
   полностью пересоздавало движок: сбрасывались позиция, стадия, монеты,
   счётчик смертей, а мультиплеерный sync терял прогресс игрока.
2. **Расхождение движков.** Движок лаунчера не имел `setSoundFxEnabled` /
   `setSoundVolume` (в `GreenBloxENGINE` они были) — звуковой API двух
   «движков» разошёлся.
3. **Утечка GPU-памяти в студии.** `refreshSelectionBoxesFromSet()` вызывается
   каждый кадр, а старый `ensureOutline` при каждом кадре создавал НОВЫЙ
   `EdgesGeometry` для выбранных объектов и диспозил старый → постоянный
   аллокатор на кадр и риск фрагментации GPU-памяти.
4. **Утечка ресурсов студии.** `dispose()` не снимал DOM-обработчики событий
   с canvas, не диспозил TransformControls/water/чекер-текстуру — повторный
   mount мог повесить дублирующиеся листенеры.

### Что сделано

- [x] **GameSession**: движок создаётся один раз на сессию. Ключ пересоздания —
      сложный ключ мира (`world:parts:spawn:sky:void`), цвета аватара больше
      не пересоздают движок. Цвета применяются через `setAvatarColors`.
      При старте сессии `avatarColors` синхронизируется с переданными цветами.
- [x] **RobloxEngine (лаунчер)**: добавлены `setSoundFxEnabled(enabled)` и
      `setSoundVolume(0..1)` — API приведён к GreenBloxENGINE.
- [x] **Студийный рендерер**: `EdgesGeometry` кэшируется и пересоздаётся только
      при реальной смене исходной геометрии (`sourceUuid`).
- [x] **Студийный рендерер**: полный `dispose` — снятие DOM-обработчиков
      (`domEventHandlers`), `transformControls.dispose()`, очистка хелперов,
      диспоз воды и чекер-текстуры, удаление всех мешей сцены.

### Проверка

- [x] `npm run typecheck --prefix greenblox-studio` — чисто.
- [x] `npm run build --prefix "greenblox launcher"` — чисто (1 023 kB, gzip 267 kB).
- [x] `npm run build --prefix GreenBloxENGINE` — чисто (789 kB, gzip 211 kB).

## 15.08.2026 — Мультиплеер: гость догружает мир хоста; утечки слушателей; чистота движков

### Найденные баги

1. **Гость входил в НЕ тот мир.** `App.handleJoinByCode` искал проект только среди
   локально загруженных (`studioProjects`). Если хост опубликовал проект ПОСЛЕ
   запуска лаунчера (или список не успел обновиться), гость по коду заходил в
   дефолтный обби, а не в плейс хоста. Догрузки проекта по `placeId` с сервера не было.
2. **CORS отсутствовал на `/api/projects/[id]`.** Список проектов
   (`/api/projects`) уже отдавался с `Access-Control-Allow-Origin`, но одиночный
   GET по id — нет. Любая попытка догрузить мир из браузера лаунчера падала бы на CORS.
3. **Утечки DOM-слушателей в движке лаунчера.** `dispose()` снимал только часть
   листенеров: не снимал `mousedown`, `contextmenu` (вешался анонимно, его вообще
   нельзя было снять) и `wheel` с canvas. Повторный вход в игру оставлял
   дублирующиеся обработчики.
4. **GreenBloxENGINE отставал по утечкам.** Автономный движок не снимал
   `contextmenu` (анонимный) и не освобождал GPU-геометрии/материалы мира,
   аватара, ghost и облаков при dispose; также не очищал «залипшие» клавиши
   при паузе — после закрытия меню персонаж мог продолжать идти.
5. **Мёртвый код в лаунчере.** `AvatarPanel.tsx` (не импортировался нигде —
   в игре используется `AvatarEditor` внутри `GameMenu`) и `PreviewHome.tsx`
   (утраченная версия главного экрана) — нигде не использовались.
6. **Фантомные вкладки.** `probe.ts`, `probe2.ts`, `loginApi.ts` в студии и
   `src/app/api/p`, `greenbloxengine/tsconfig.json` в корне — в файловой системе
   их не существует (остатки закрытых вкладок/опечаточных путей).

### Что сделано

- [x] **Студия**: `/api/projects/[id]/route.ts` — добавлены CORS-заголовки на
      все методы (GET/PUT/DELETE/OPTIONS) + `Access-Control-Allow-Headers: x-gbtoken`.
- [x] **Launcher**: `App.tsx` — добавлен `fetchStudioProject(id)` (догрузка одного
      проекта по id). `handleJoinByCode` теперь: сначала ищет проект в локальном
      списке; если нет — догружает с сервера по `placeId` сессии и конвертирует
      мир; если и это не вышло — показывает дефолтный мир (obby). Гость всегда
      попадает в мир хоста.
- [x] **Движок (лаунчер)**: `dispose()` — снимает `mousedown`, `contextmenu`,
      `wheel`; `contextmenu` вынесен в именованный обработчик `onContextMenu`.
- [x] **Движок (GreenBloxENGINE)**: синхронизирован с лаунчером —
      полное `dispose` (траversal-релиз геометрий/материалов мира, аватара, ghost,
      облаков), снятие `contextmenu` через именованный обработчик, `keys.clear()`

- [x] **Уборка**: удалены неиспользуемые `AvatarPanel.tsx`, `PreviewHome.tsx`
      и дубликат студии `preview/`.
- [x] Проверены импорты удалённых компонентов — ни одного ссылающегося файла
